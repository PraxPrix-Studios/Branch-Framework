guide/network

Networking

You declare what travels between the server and players. Branch Studio turns those declarations into specialised code that writes every value into buffers, batches a frame's events into one remote call per player, and validates everything a client sends.

Turn it on

In Branch Studio's Overview page, switch on Compiled networking. The plugin then keeps Branch.Network up to date as you type. Until it is on, reading Branch.Network raises an error that tells you so.

Declare

Add a Network table to a server segment:

local CombatService = {}

CombatService.Network = {
	Hit    = { From = "Client", Type = "Unreliable", Data = { Target = "Instance(Model)", Power = "f32(0..1, 0.01)" } },
	Damage = { From = "Server", Data = { "u16", "boolean" } },      -- two arguments
	Move   = { From = "Server", Unpack = true, Data = { pos = "vector", yaw = "f32" } },
	Buy    = { Data = "string(..32)", Return = "boolean" },         -- a function
	Ready  = { From = "Client" },                                   -- no data
}

return CombatService
Write it as a plain table. The plugin reads the declaration from your source code, so it must be a literal table: no variables, loops or function calls inside it.

Latest: only the newest value

For state that is sent often (a position, health, an animation), only the newest value matters. With Latest = true, if you fire the same event to a player three times in one frame, only the third one is sent; the two older ones are dropped before they cost anything.

Position = { From = "Server", Type = "Unreliable", Latest = true, Data = { id = "u16", pos = "vector" } },
  • Per recipient. "Newest" means per player. After FireAll, a newer Fire to one player also reaches that player; a FireAll after single Fires replaces them.
  • Per key. With Delta and a Key, "newest" is per object: fire 50 units in one frame and all 50 arrive, each with its newest value.
  • End of the frame. Latest events are written when the frame ships, so they arrive after the frame's other events.
  • Reuse your table. A struct you pass is copied, so you may change the same table and fire it again for the next object.
  • Not for functions. Every function call needs its own answer, so Latest only works on events. It works in both directions.

Hz: a fixed number of sends a second

Many things are fired every frame but nobody needs them 60 times a second. Hz = 20 keeps the newest value and sends it 20 times a second: a third of the traffic, with no change to your code.

Stamina = { From = "Server", Hz = 10, Data = "u8" },
Aim     = { From = "Client", Hz = 20, Type = "Unreliable", Data = "vector" },
  • Includes Latest. Between sends, only the newest value is kept, and it is the one that goes out.
  • Nothing is lost. The last value you fired always arrives, at the next send.
  • No wait after a pause. When the event has been quiet, a new value goes out at once.
  • Any number up to 60, fractions included: Hz = 0.5 is once every two seconds.

Lod: often near, rarely far

A monster next to you should move smoothly; one 300 studs away can update a few times a second. Lod sets that per distance, and FireFrom(position, ...) sends to every player at the rate of the ring their character is in.

Mob = { From = "Server", Delta = true, Key = "id", Lod = { { 50, 30 }, { 200, 5 } }, Data = { id = "u16", pos = "vector", hp = "u8" } },
-- in Heartbeat: every mob, from its own position
for id, mob in mobs do
	Net.Mob.FireFrom(mob.Position, { id = id, pos = mob.Position, hp = mob.Hp })
end
  • Rings, near to far. { 50, 30 } means "within 50 studs, 30 times a second". Players beyond the last ring, or without a character, get nothing from FireFrom.
  • Newest value per player. When a player's ring allows a send, they get the newest value, so a far player sees the mob jump to where it is now.
  • The other sends still work. Fire, FireAll and the rest ignore distance (and use Hz, if the event has it).
  • Server → client only: the server knows where everyone is.

Delta: only what changed

With Delta = true, a struct travels in full the first time, and after that only the fields that changed since the last send to that recipient. A character standing still costs almost nothing, and a changed boolean costs no bytes at all: its "changed" bit already says it flipped.

Unit = { From = "Server", Delta = true, Key = "id", Data = { id = "u16", pos = "vector", hp = "u8", stunned = "boolean" } },
  • Key names the field that tells objects apart. Each key has its own state, so one event can carry many units. Without Key, there is one state per recipient.
  • Listeners always get the full struct. The receiver fills in the unchanged fields itself, so your code never sees a partial value.
  • Forget(key) drops the state kept for a key: call it when the object is gone, so neither side keeps it in memory. The next send for that key goes out in full. Without Key, Forget() makes the next send to every player full.
  • Reliable only. A lost unreliable packet would leave the receiver with the wrong state, so the compiler refuses Delta on Unreliable events.
  • Tables inside the struct (arrays, maps, nested structs) are sent whenever the struct is sent: comparing them would cost more than it saves.
  • FireAll on a Delta event writes to each player separately, because every player can hold a different state (someone who just joined gets the full struct).

Delta works with Latest, Hz and Lod: only the newest value is compared and sent.

Threshold: ignore tiny moves

Physics makes positions jitter by fractions of a stud, and Delta would send every jitter. With a Threshold, a number or vector that moved less than that still counts as unchanged.

Unit = { From = "Server", Delta = true, Threshold = { pos = 0.05, hp = 1 }, Data = { pos = "vector", hp = "f32", name = "string" } },
Bar  = { From = "Server", Delta = true, Threshold = 0.5, Data = { x = "f32", y = "f32" } },   -- every number field
  • Small moves add up. The comparison is with what the receiver has, not with the last frame, so many small moves are sent as soon as together they pass the threshold. The receiver is never further off than the threshold.
  • What it covers. Number and vector fields (optional ones too). A vector counts as moved when any of its three components moved further than the threshold. NaN always counts as a change.
  • Exactly the threshold still counts as unchanged: with Threshold = 1, 5 → 6 is not sent, 5 → 7 is.

FireNear: only players nearby

Net.Explosion.FireNear(position, 150, damage)   -- players whose character is within 150 studs

Every server → client event has FireNear(position, radius, ...). It checks each player's Character.PrimaryPart; players without a character are skipped. In a big map, the savings grow with the number of players. For things that far players should still see, now and then, use Lod instead.

Pack: small values as bits

Normally every value takes whole bytes: a number from 0 to 100 takes 1 byte (8 bits) though it needs 7. With Pack = true, small values are written as bits, one after another.

Bag = { From = "Server", Pack = true, Data = "{ id: u16(0..1000), count: u8(0..99), rarity: enum(Common, Rare, Epic), fav: boolean }[]" },

Each item above takes 10 + 7 + 2 + 1 = 20 bits instead of 5 bytes (40 bits): 200 items go from 1,000 bytes to about 500.

  • What shrinks: booleans, enum(...), stepped numbers, whole numbers with a range (u8(0..100), u32(0..5000)), u8 / i8 / u16 / i16, optional flags, and lengths of arrays with a maximum (u8[..64]).
  • The narrower the range, the smaller: u8(0..9) is 4 bits, u8(0..1) is 1. Declare the real range of your values.
  • Everything else still works (floats, vectors, strings, Instances): they are written as bytes, after the bits before them.
  • When to use it: inventories, maps, grids, stats: lists of small numbers. It saves nothing on floats and vectors, and writing bits costs a little more time than writing bytes, so it is not the default.
  • Not with Delta (Delta already sends only what changed), and not on functions.

The server still checks every packed value against its declared range: 7 bits can hold 127, but a u8(0..100) above 100 is rejected.

Rate: limit what clients send

Validation checks that a packet is correct. Rate also checks how often a player sends it, so an exploiter cannot spam valid events.

Attack = { From = "Client", Rate = "10/s", Data = { dir = "vector" } },
Buy    = { Data = "string(..32)", Return = "boolean", Rate = "30/m" },
  • How it counts. Each player gets a bucket of that many sends, refilled at that rate. A short burst up to the limit is fine.
  • Over the limit, events are dropped before any listener sees them, and a function answers "failed", so the client's Invoke errors.
  • OnReject hears about it at most once a second per player and event, with a reason that starts with rate limit:.
  • Only on From = "Client" events and functions: the server does not need a limit on itself.

Use

-- server
local Net = Branch.Network.Server.CombatService

Net.Damage.Fire(player, 25, true)                 -- one player
Net.Damage.FireAll(25, true)                      -- everyone
Net.Damage.FireList({ a, b }, 25, true)           -- a list of players
Net.Damage.FireExcept(player, 25, true)           -- everyone but one
Net.Damage.FireNear(position, 100, 25, true)      -- players within 100 studs
Net.Mob.FireFrom(position, mob)                   -- Lod events: rate by distance
Net.Hit.On(function(player, hit) end)             -- client -> server event
Net.Buy.On(function(player, item) return true end) -- a function's handler

-- client
local Net = Branch.Network.Client.CombatService

Net.Hit.Fire({ Target = model, Power = 0.8 })
Net.Damage.On(function(amount, crit) end)
Net.Move.On(function(pos, yaw) end)
local ok = Net.Buy.Invoke("sword")                -- yields for the answer
  • On for events returns a function that disconnects the listener. An event can have many listeners.
  • On for functions sets the one handler. Setting it again replaces it.
  • Invoke raises an error on the client if the server's handler errored. It also errors if the call could not be queued.

How it travels

  • Batched per frame. Everything you fire for a player in one frame leaves as one remote call. FireAll goes out once, through FireAllClients.
  • Exact order. Each player receives events in the order they were fired, even when Fire, FireAll and FireList are mixed.
  • Compact.
    • Booleans and optional flags are packed into bits, and short lengths take one byte.
    • A repeated event is written without its id; the id goes once for the whole run.
    • Stepped numbers such as f32(0..1, 0.01) travel as a small step index.
    • With Pack, small numbers and enums are written as bits too.
  • Unreliable under the limit. Unreliable events are batched into packets under a safe budget (820 bytes by default). Roblox drops unreliable packets above about 900 bytes. Unreliable traffic sent during the first seconds of a join can be dropped while Roblox replicates the world, so use Reliable for anything that must arrive.
  • Function calls go out at once and do not wait for the end of the frame.

Safety

  • Everything from clients is validated before any listener sees it: bounds, ranges, NaN and infinity, enum values, Instance classes, string and array lengths (checked before anything is allocated) and packet size.
  • Rejected packets. A malformed packet is dropped and reported through Branch.Network.OnReject, so you can log or kick: 
    Branch.Network.OnReject(function(player, reason)
	warn(player.Name, "sent a bad packet:", reason)
end)
  • Bad arguments. A bad argument to Fire errors at your call and never corrupts the other events of the frame. These argument checks run in Studio by default (Settings → Network → Argument checks).
  • Errors in your own Sync listener are your game's bug, not the player's. The error is printed with its traceback, OnReject is not called, and the rest of the packet is still delivered.
  • Before a listener exists. Events that arrive before anyone listens are queued (256 by default) and delivered when a listener connects. A function call that finds its queue full is answered with a failure instead of hanging.

See the traffic

While you Play in Studio, Branch Studio opens a Branch Network (live) window. It shows:

  • Every event, both directions: how many times it is sent per second, its bytes per second and its share of the traffic, busiest first. The top rows are where the Send less options pay off most.
  • Smaller types. Hints such as "hp is always a whole number from 0 to 200: declare it as u8 instead of u32 to save 3 B per value".

Apply the hints with one click

  1. On the Network page of Branch Studio, press Profile. Play starts as usual.
  2. Play the game: fight, buy, die, so every event sends its typical values.
  3. In the Branch Network (live) window, press Finish. Play stops and the hints go to Branch Studio.
  4. On the Overview page, each hint is listed under Problems. Click one: the type in your declaration is changed (one undo step) and the network is compiled again.

Hints stay under Problems until you apply them, even after Studio restarts. A hint is refused if the declaration changed since (say, the field was renamed), or if the smaller type cannot hold a range you declared. The Log says why.

Why a Profile button, and not the normal Play? Play runs in a copy of your place, and a Studio plugin cannot pass data from that copy back to the place you edit. Play started with Profile can: Finish ends it and hands the hints back.

The counters only run in Studio: in a live server they are switched off. Turn the window off in Settings → Editor → Live network profiler (Profile always shows it).

Where the code lives

  • ReplicatedStorage.Packages.Branch.Network: the entry module, the client half and the two remotes.
  • ServerScriptService.BranchNetworkServer: the server half. Players never download it, so a big game does not make every player load the server's code, and exploiters cannot read the server's checks. Its Root value points back at Branch.Network.

Branch Studio writes both and keeps them in sync. Places compiled by earlier versions are moved over on the next compile.

Where the plugin looks

  • Which folders. Branch Studio reads declarations from the roots in Settings → Paths (ServerScriptService.Services by default). If your game passes other folders to Branch:Start, set them there too: the plugin cannot know what the game will pass at run time.
  • Mistakes. Luau keywords (end, local, …) are refused as names. A mistyped Enum(...) is an error, and an unknown Instance(...) class is a warning. While a declaration has an error, the last working Branch.Network stays in place.
  • Outside a running game (plugins, the command bar), every Branch.Network call does nothing, so tooling that requires your services does not break.
