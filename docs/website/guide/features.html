Using the features

Every feature from Unique features, step by step: how to turn it on, a full example, the rules, and how to check that it works. Features marked automatic need nothing from you.

Before you start. Networking features are declared in a service's Network table and compiled by Branch Studio as you type. If you have not declared an event yet, read Networking first.

Networking you declare

Declared inside your services

  1. Open a server segment (any module named …Service).
  2. Add a Network table with your events: 
    local ShopService = {}

ShopService.Network = {
	Bought = { From = "Server", Data = { item = "string(..32)", coins = "u32" } },
	Buy    = { Data = "string(..32)", Return = "boolean" },   -- a function: client asks, server answers
}

return ShopService
  3. Stop typing for a moment: Branch Studio compiles it. Use it from the server as Branch.Network.Server.ShopService and from the client as Branch.Network.Client.ShopService.

Check: the event appears on the plugin's Network page, and autocomplete knows its arguments.

Stepped numbers

Say how precise a number needs to be, and Branch sends the step number instead of the full value.

  1. Write the type as type(min..max, step): 
    Aim = { From = "Client", Type = "Unreliable", Data = {
	pitch = "f32(-90..90, 0.5)",   -- 361 steps  -> 2 bytes instead of 4
	charge = "f32(0..1, 0.01)",    -- 101 steps  -> 1 byte instead of 4
} },
  2. Send normal numbers: Net.Aim.Fire({ pitch = 12.3, charge = 0.5 }). The receiver gets the value rounded to the nearest step (12.5).
  • Size. Up to 256 steps take 1 byte, up to 65,536 take 2, more take 4.
  • Pick the coarsest step you can live with. The profiler (smaller-type hints) tells you the real range of your values.
  • Out of range. A client value outside min..max is rejected on the server and reported to OnReject.

Runs automatic

Fire the same event several times in a row (say, 50 hit markers) and its id is written once for the whole run instead of once per event. Nothing to turn on: fire events as usual. Runs form when the same event is fired three or more times in a row to the same player.

Packed booleans automatic

All booleans in a struct and all "is this optional value here" flags share one bit mask, and boolean arrays pack 8 per byte. Declare them normally: Data = { crouch = "boolean", sprint = "boolean", target = "Instance(Model)?" } costs one byte of flags.

One FireAllClients per frame automatic

Call FireAll as often as you like: a frame's broadcasts are written once and shipped in one FireAllClients. Mixing FireAll with Fire to single players is safe: each player still receives everything in the order you fired it.

Unreliable, batched safely automatic

Declare Type = "Unreliable" for things that may be lost (positions, effects). Branch groups a frame's unreliable events into packets that stay under Roblox's limit (820 bytes by default), instead of one remote call per event.

Unreliable can be lost, especially in the first seconds after a player joins. Anything that must arrive (purchases, deaths, state changes) should stay Reliable.

Errors that stay contained automatic

  • A wrong argument to Fire errors at your call, with the event's name, and the rest of the frame is sent normally. These checks run in Studio by default (Settings → Network → Argument checks).
  • If one of your listeners throws, the error is printed with its traceback and the other events in the packet are still delivered.

Send less

Latest

For state that changes all the time (a position, a health bar, an aim direction), only the newest value matters. With Latest, several sends to the same player in one frame become one: the newest.

  1. Add Latest = true to the event: 
    Position = { From = "Server", Type = "Unreliable", Latest = true, Data = "vector" },
  2. Fire it as usual, as often as your code wants to. You do not need to track "did I already send this frame": 
    -- server: called from several systems in the same frame
Net.Position.Fire(player, walkTarget)
Net.Position.Fire(player, knockbackTarget)   -- only this one is sent
  3. The client listens normally: Net.Position.On(function(pos) ... end).
  • "Newest" is per player. A FireAll replaces earlier single sends of that frame; a Fire to one player after a FireAll also reaches that player.
  • Sent at the end of the frame, after the frame's other events. Don't use it for an event whose order relative to other events matters.
  • Works both ways (server → client and client → server), but not on functions: every call needs its own answer.

Check: in the live profiler (Play in Studio), the event's sends per second stop growing past your frame rate.

Delta

The first send carries the whole struct. After that, only the fields that changed since the last send to that player travel. A character standing still costs almost nothing.

  1. The event must be Reliable (the default) and its Data must be a struct. Add Delta = true: 
    Stats = { From = "Server", Delta = true, Data = { hp = "u8", mana = "u8", stunned = "boolean", zone = "string(..24)" } },
  2. Fire the full struct every time. Branch works out what changed: 
    -- server, e.g. in Heartbeat
Net.Stats.Fire(player, { hp = hum.Health, mana = mana, stunned = stunned, zone = zoneName })
  3. The client always receives the full struct, with unchanged fields filled in for you: 
    Net.Stats.On(function(s)
	healthBar.Size = UDim2.fromScale(s.hp / 100, 1)
end)

Many objects in one event: Key

To send many units, projectiles or doors through one event, name the field that tells them apart. Each key keeps its own state:

Unit = { From = "Server", Delta = true, Key = "id", Data = { id = "u16", pos = "vector", hp = "u8", stunned = "boolean" } },
-- server
for id, unit in units do
	Net.Unit.FireAll({ id = id, pos = unit.Position, hp = unit.Hp, stunned = unit.Stunned })
end

-- when a unit dies: drop its state on both sides
Net.Unit.Forget(id)

-- client
Net.Unit.On(function(u)
	local model = models[u.id]
	model:PivotTo(CFrame.new(u.pos))
end)
  • Always call Forget(key) when an object is gone, or both sides keep its state in memory. The next send for that key goes out in full. Without Key, Forget() makes the next send to every player full.
  • The key must be a plain value (a number, string, …), not optional and not a table.
  • Limits. Reliable only (a lost unreliable packet would leave the client with a wrong state); up to 32 fields besides the key.
  • Tables inside the struct (arrays, maps, nested structs) are sent every time: comparing them would cost more than it saves. Put things that change rarely in their own Delta event.
  • New players automatically get the full struct first, even through FireAll.
  • With Latest = true as well, only the frame's newest value is compared and sent.

Check: in the live profiler, the event's bytes per second drop sharply while nothing changes.

Booleans that cost zero bytes automatic

In a Delta event, a boolean that changed is not sent at all: its "changed" bit already tells the receiver to flip it. Just declare booleans in a Delta struct:

Door = { From = "Server", Delta = true, Key = "id", Data = { id = "u16", open = "boolean", locked = "boolean" } },
-- opening a door sends: id + one mask byte. The "open" value itself costs 0 bytes.

This is a good reason to turn flags like open, stunned or visible into booleans in a Delta event, instead of sending separate events for them.

FireNear

Send only to players whose character is within a radius: explosions, footsteps, local sounds, hit effects.

  1. Nothing to declare: every server → client event has FireNear.
  2. Pass a position, a radius in studs, then the event's arguments: 
    -- server
Net.Explosion.FireNear(position, 150, position, damage)
  • Distance is measured to each player's Character.PrimaryPart. Players without a character (dead, loading) are skipped.
  • Choose the radius by what players can see or hear. Too small, and players at the edge miss the effect.
  • With Latest and Delta it works like FireList: each nearby player is handled separately.

Check: with two test players far apart (Test → Clients and Servers), only the near one receives the event.

Security

Everything from clients is validated automatic

Your declaration is the rulebook. Whatever you declare for a From = "Client" event is enforced on the server before any listener runs: u8 can't be 300, string(..32) can't be 10,000 characters, Instance(Tool) can't be a Part, NaN and infinity never get through. The tighter your types, the less an exploiter can send.

Hit = { From = "Client", Data = { target = "Instance(Model)", power = "f32(0..1, 0.01)" } },
-- on the server, target is always a Model and power is always 0..1

Rate limits

Validation checks that a packet is correct; Rate checks how often a player sends it.

  1. Add Rate to client → server events and functions, as "N/s" or "N/m": 
    Attack = { From = "Client", Rate = "10/s", Data = { dir = "vector" } },
Buy    = { Data = "string(..32)", Return = "boolean", Rate = "30/m" },
  2. Listen as usual. Extra events never reach your listener; an extra function call answers "failed", so the client's Invoke errors: 
    -- client
local ok, err = pcall(Net.Buy.Invoke, "sword")
  3. Optionally, react to spammers through OnReject.
  • Bursts are fine. Each player has a bucket of N sends that refills at that rate, so a short burst up to the limit passes.
  • Set it a bit above honest play. If your gun fires 8 times a second, use "12/s", not "8/s": network jitter can bunch honest sends together.

Server code never reaches players automatic

Branch Studio writes the server half of the network to ServerScriptService.BranchNetworkServer. Players never download it, so they can't read your server checks, and a big game doesn't make every player load server code. You don't move or require anything: keep using Branch.Network.Server. Places compiled with older versions are moved over on the next compile.

Don't move or rename BranchNetworkServer or its Root value. The plugin rewrites them on each compile.

OnReject

One place to hear about every malformed packet and every rate-limit breach. Put it in a server segment's Init or Start:

local strikes = {}

Branch.Network.OnReject(function(player, reason)
	warn(player.Name, "rejected:", reason)
	if string.find(reason, "^rate limit:") then
		strikes[player] = (strikes[player] or 0) + 1
		if strikes[player] >= 5 then
			player:Kick("Too many requests")
		end
	end
end)
  • Rate-limit reasons start with rate limit: and name the event. They are reported at most once a second per player and event.
  • Other reasons (bad sizes, out-of-range values, unknown events) come from broken or forged packets. A normal client never sends them, so they are safe grounds for a kick.

Branch Studio

Live compiler automatic

Install Branch Studio and press Install on its Overview page. From then on, whenever you stop typing, it rebuilds typed autocomplete for GetSegment and data paths, and Branch.Network. Everything lands in one undo step: Ctrl+Z undoes a compile. To compile by hand, press Compile on the toolbar; Live turns compiling as you type on and off.

Bytes per fire, before you run automatic

Open the plugin's Network page: each event shows its direction, reliability, and how many bytes one send costs. Change a type and watch the number change: it is the fastest way to choose between, say, u16 and f32(0..100, 0.5). Click an event to open its declaration.

Live network profiler

  1. Press Play in Studio. The Branch Network (live) window opens.
  2. Play the game normally. Every second the window updates each event, in both directions: sends per second, bytes per second, and share of the total, busiest first.
  3. Start with the top rows: those events are where savings matter. Typical fixes: Latest for events sent several times a frame, Delta for state that rarely changes, FireNear for local effects, stepped numbers for precise numbers.
  • Zero cost in live games. The counters only run in Studio.
  • Turn it off in Settings → Editor → Live network profiler.

Smaller-type hints

Under the traffic table, the profiler lists numbers that could travel smaller, based on the values your game really sent:

Combat.Hit.damage is always a whole number from 0 to 200: declare it as u8 instead of u32 to save 3 B per value.
  1. Play long enough to see the real range (fight, buy, die: whatever the event covers).
  2. Change the type in the declaration to the suggested one, leaving some headroom if the values can grow later.
  3. Play again: the hint disappears, and the event's bytes per second drop.

Hints cover whole numbers in bigger types, f64 that fits in f32, and numbers that would fit a stepped type.

Smart rename

Rename a module in the Explorer as usual. Branch Studio carries the new name through your code in one undo step: the module's table name, GetSegment("Old"), Dependencies, and paths like script.Parent.Old or :WaitForChild("Old") that really lead to it. Anything it could not update safely (a path through a variable, a chain split across lines) is listed in the Log: click each entry and fix it by hand.

Engine names checked while you type automatic

Write Enum(KeyCode) or Instance(Model) in a declaration. A misspelled enum is an error in Problems (the last working network stays in place), and an unknown class is a warning.

Templates for new modules

Create a ModuleScript named …Service or …Controller: it is filled from your template, with {NAME} replaced by the module's name. Edit the templates in Settings → Templates.

Safe install and update

Press Update on the Overview page when a new runtime is available. Files that are no longer shipped are removed; files you edited by hand are first copied to ServerStorage.BranchBackups. Generated files and settings are kept.

Light on slow machines automatic

The plugin re-reads only changed modules and waits longer between compiles on slow computers. To also turn off every animation, enable Settings → Editor → Reduce motion.

Player data

Template checks all the way down automatic

Start data with a Template (see Player data). Every write is then checked against it, including nested tables: Data.Set(player, "stats.kills", "ten") errors at that line instead of breaking the save later.

No NaN, no infinity automatic

Data.Set(player, "ratio", kills / deaths) with 0 deaths errors at the call instead of silently making every later save fail. Guard divisions where they happen.

Migrations on a copy

When you rename or reshape a field, add a function to Migrations. Each one upgrades a profile by one version:

Migrations = {
	function(data) data.gold = data.coins; data.coins = nil end,   -- v0 -> v1: coins renamed to gold
},

If a migration errors, the saved data is untouched and the player is asked to rejoin. Only ever append: never edit or reorder a migration that already shipped.

Template change warnings

  1. Point Settings → Paths → Data template at your template module.
  2. When you remove a field or change its type, Problems shows a warning: saved player data will not follow on its own.
  3. Write the migration, then click the warning to accept the new shape.

New fields need nothing: they are added to old saves automatically, so they never warn.

Writes on the way out automatic

A segment's PlayerRemoving hook can still write the leaving player's data, and it is saved with the session. Write before the hook yields (task.wait, web calls).

Observers that see everything

Data.Observe(player, "stats.kills", function(new, old) end)   -- also fires when the whole "stats" is replaced
Data.Get(player, "friends.12345")                              -- reaches dictionaries keyed by UserId

A DataStore browser that protects players

  1. Open the plugin's DataStores page. Pick a store, then a key.
  2. Browse freely: live data is read-only. Old versions, the 4 MB size meter and ProfileStore session locks are shown.
  3. To edit, restore a version or delete, click the lock twice. Writes stay allowed until Studio closes. A profile that is in use, or changed since you opened it, is never overwritten.

To try the page without real data, press Try sample: it is always editable.

The framework

Segments by name automatic

Name a module …Service (server) or …Controller (client), anywhere under the roots you pass to Branch:Start, and it is loaded. Any other module is a helper you require yourself. Details: Segments.

A strict, readable lifecycle automatic

Put setup that others rely on in Init, and list what you need in Dependencies: those segments' Init runs first. Loops and waiting go in Start. Player and frame work goes in hooks (PlayerAdded, Heartbeat, …), which share one engine connection per hook type.

Failures you can see automatic

Watch the Output: a slow Init warns after 5 seconds, a failed dependency is named, and a typo like Branch.Netwrok errors instead of returning nil. Branch:GetReport() returns every segment in load order with its status and Init time.
