Segments

A segment is a ModuleScript that returns a table. On the server they are your services, on the client your controllers. Branch finds them, starts them in the right order and wires up their hooks.

Which modules are segments

Branch looks under the roots you pass to Branch:Start and decides which modules are segments with a segment rule:

RuleSegmentsEverything else
"Suffix" (default)Every ModuleScript under the roots whose name ends with Service (server) or Controller (client), at any depth and in any casing: ShopService, shopService, shop_service, SHOP_SERVICE. Services can nest inside services.Helpers. They are never loaded on their own; require them yourself.
"Folders"Modules directly under a root, or under Folders inside it.A module parented to another module is that module's private helper.
Branch:Start(script.Parent.Services)                               -- rule from Branch Studio, else "Suffix"
Branch:Start(script.Parent.Services, { SegmentRule = "Folders" })  -- explicit

You choose the rule in Branch Studio (Settings → Paths → Segment rule). The plugin stores it as the SegmentRule attribute on the Branch module, so the plugin and the runtime always agree. An options table passed to Start wins over the attribute.

Forgot the suffix? Under "Suffix", a module with Init or Start whose name does not end in Service/Controller (say ShopManager) is not loaded. Branch Studio lists it as a warning.

The lifecycle

  1. Load. Every segment is required. A module that errors or does not return a table is reported and skipped.
  2. Init. Each segment's Init runs one at a time, in dependency order. Init may yield, and everything after it waits.
  3. Start. After every Init has finished, each segment's Start runs in its own thread, so a Start that loops forever does not block the others.
  4. Hooks. Player and frame hooks are connected.
local ShopService = { Dependencies = { "PlayerService" } } -- Init runs after PlayerService:Init

function ShopService:Init() end                 -- sequential, dependency-ordered, may yield
function ShopService:Start() end                -- each in its own thread, after every Init
function ShopService:PlayerAdded(player) end    -- players already in game + every future join
function ShopService:PlayerRemoving(player) end -- can still read/write the player's data
function ShopService:Heartbeat(dt) end          -- also PreSimulation, PreRender (client)

return ShopService

Branch:AwaitStart() yields until all of this is done. Branch:GetPhase() tells you where Branch is: "Idle", "Loading", "Initializing" or "Started".

Dependencies

List the names of segments whose Init must run before yours:

local ShopService = { Dependencies = { "PlayerService", "InventoryService" } }
  • Segments without dependencies keep their discovery order.
  • A name that is not a segment, or a cycle (A needs B, B needs A), is reported in red. Branch still starts everything else.
  • Dependencies only orders Init. Every Start runs after every Init anyway.

Hooks

HookWhen
PlayerAdded(player)For every player already in the game when Branch starts, then for every new player. Each call runs in its own thread.
PlayerRemoving(player)When a player leaves. On the server, Branch.Data still has their data: writes made before the hook yields are saved with the session.
Heartbeat(dt)Every frame, after physics.
PreSimulation(dt)Every frame, before physics.
PreRender(dt)Every frame, before rendering. Client only.

Frame hooks share one engine connection per hook type, however many segments use them. A hook that errors is reported (at most once every 5 seconds per segment) and does not stop the other segments' hooks.

Finding other segments

function ShopService:Init()
	self.Players = Branch:GetSegment("PlayerService")
	local found = Branch:LocateSegments({ "InventoryService", "CoinService" })
end
  • Where to look segments up. Do it in Init or later, not at the top of the module: while modules are still loading, the one you want may not be loaded yet. An unknown name is an error, not nil.
  • Autocomplete. With Branch Studio, GetSegment is typed per segment, so Branch:GetSegment("ShopService"):Buy(…) autocompletes.

When something goes wrong

  • A failing Init marks the segment Failed. It is not started and its hooks are not connected. Segments that depend on it still start, with a warning that names the failed dependency.
  • A slow require or Init that is still running after 5 seconds gets a warning, since everything after it is waiting. The usual cause is a WaitForChild or DataStore call that never returns.
  • Two segments with the same name are an error: the second is skipped and the message names both paths.
  • A typo on Branch such as Branch.Netwrok is an error instead of a silent nil.
  • A bad argument to Branch:Start errors before anything starts, so you can fix it and call Start again.
