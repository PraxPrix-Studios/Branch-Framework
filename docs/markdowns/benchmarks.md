# Branch Network: benchmarks and tests

Branch Network is the compiled networking layer of Branch. You declare events on your services, and the Branch Studio plugin generates the serialisation code for them. We compared it with the two best-known libraries of the same kind:

- **NetRay** (NetRay-Compile 0.1.1)
- **Blink** (v0.17)

All three libraries were given the same schemas, the same data and the same machine. Everything below was measured on **24 September 2026 with Branch 2.0.0**.

**How to read "X% faster".** If Branch is "50% faster than NetRay", NetRay needs 50% more time than Branch for the same work. For example, Branch takes 1.0 ms and NetRay takes 1.5 ms. "0%" means a tie.

**Two parts.** The tests have two parts, and each answers a different question:

1. **Lune**: the generated code, run outside Roblox. Clean, repeatable numbers with no engine noise, good for comparing the code itself.
2. **Roblox Studio**: the real engine, a real server and a real client. These numbers show what happens in an actual game.

---

## Summary

| Case | vs NetRay | vs Blink |
|---|---:|---:|
| **Lune:** NetRay's own benchmark (cars) | 54% faster | 77% faster |
| **Lune:** 1000 booleans ×10 per frame | 155% faster | 63% faster |
| **Lune:** entities (100 small structs ×10 per frame) | 139% faster | 167% faster |
| **Lune:** chat (string + number) ×500 per frame | 95% faster | 62% faster |
| **Lune:** server → 1 player ×500 per frame | 39% faster | 87% faster |
| **Lune:** FireAll to 20 players ×50 per frame | 6% faster | 36% faster |
| **Lune:** unreliable ×200 per frame | 50% faster | 69% faster |
| **Studio:** client → server, 50 cars per frame | 20% faster | 36% faster |
| **Studio:** server reads those cars | 21% faster | 247% faster |
| **Studio:** server → 1 player, 100 per frame | 427% faster | 42% faster |
| **Studio:** FireAll, 100 per frame | 24% faster | 125% faster |
| **Studio:** client reads a FireAll frame | 18% faster | 676% faster |
| **Studio:** round trip of a function call | tie | tie |

Branch was faster in every case except the function round trip, which is a tie for all three because it is limited by the network, not by the code. Branch also sends the same or fewer bytes in every case, and it **validates everything a client sends**, which NetRay does not do by default.

# Part 1: Lune

## How we tested

- **Same generated code.** Each library's code was generated by its own compiler from the same schema: the Blink CLI for Blink, the NetRay CLI for NetRay, and the Branch Studio compiler for Branch.
- **Mocked Roblox.** The code ran in [Lune](https://lune-org.github.io/docs), a Luau runtime, with a small fake Roblox around it: players, `RemoteEvent`s and a frame clock. One fake server and N fake clients pass real buffers to each other through this fake "wire".
- **What was timed:**
  - **Encode**: every `Fire` call plus the end-of-frame flush that builds the packets.
  - **Decode**: receiving those packets and handing each event to an empty listener.
  - **Total**: encode + decode.
  - Also counted: the bytes on the wire and the number of remote calls per frame.
- **Runs.** Each case ran 30 warm-up frames and then 300 measured frames, repeated 5 times; the best repeat was kept. We ran the whole benchmark 3 times and kept the best value of each cell for every library. Times are **milliseconds per frame (lower is better)**.
- **Validation settings.**
  - NetRay does not validate incoming data by default, so it is shown twice: as it ships, and with `Validate=Full`.
  - Branch always validates what the server receives from clients, and its numbers include that.
- **Unpack.** Branch has an `Unpack` option that passes struct fields as plain arguments instead of a table. The headline numbers use the default setting (no Unpack); the Unpack result is given as a note.

---

### Case 1: NetRay's own benchmark (cars)

This is the test the NetRay author uses to present NetRay. Every frame, the client sends 50 "car" records to the server. Each car has a brand, a name, an id, an "available" flag, a dealer count and a price.

| Library | Encode | Decode | Total | Bytes / frame |
|---|---:|---:|---:|---:|
| **Branch** | **0.027** | **0.029** | **0.056** | 6273 |
| NetRay | 0.056 | 0.030 | 0.086 | 6273 |
| NetRay (Validate=Full) | 0.086 | 0.034 | 0.120 | 6273 |
| Blink | 0.044 | 0.055 | 0.099 | 6420 |

--- **Branch is 54% faster than NetRay, 77% faster than Blink** (114% faster than NetRay with validation on).

Decoding is about even with NetRay here; the difference is in sending. With `Unpack`, Branch's total drops to 0.051 ms.

---

### Case 2: Booleans (1000 booleans, 10 times per frame)

The client sends an array of 1000 true/false values to the server 10 times per frame. This is typical of a grid, map or inventory state stored as flags.

| Library | Encode | Decode | Total | Bytes / frame |
|---|---:|---:|---:|---:|
| **Branch** | **0.391** | **0.694** | **1.085** | **1273** |
| NetRay | 1.366 | 1.398 | 2.764 | 1273 |
| NetRay (Validate=Full) | 4.327 | 1.391 | 5.718 | 1273 |
| Blink | 0.677 | 1.089 | 1.766 | 10030 |

--- **Branch is 155% faster than NetRay, 63% faster than Blink.**

- **Size.** Branch and NetRay pack 8 booleans into one byte. Blink spends a whole byte on each boolean, so its packets are about 8 times larger.
- **Noise.** The `Unpack` build generates identical code for this case, and it measured 0.595 ms. We kept the slower number to be safe.

---

### Case 3: Entities (100 structs, 10 times per frame)

The client sends an array of 100 compact entity records to the server 10 times per frame. Each record has six small numbers: an id, x, y, z, an orientation and an animation. This is typical of sending many small records at once.

| Library | Encode | Decode | Total | Bytes / frame |
|---|---:|---:|---:|---:|
| **Branch** | **0.197** | **0.240** | **0.437** | **6013** |
| NetRay | 0.391 | 0.653 | 1.044 | 6023 |
| NetRay (Validate=Full) | 1.169 | 0.660 | 1.829 | 6023 |
| Blink | 0.352 | 0.814 | 1.166 | 6030 |

--- **Branch is 139% faster than NetRay, 167% faster than Blink.**

Branch writes every fixed-size field at a known position, with a single space check per record. This is where that pays off most.

---

### Case 4: Chat (a string and a number, 500 times per frame)

The client sends 500 short messages to the server per frame, each with a text and a number. This tests strings and many small events.

| Library | Encode | Decode | Total | Bytes / frame |
|---|---:|---:|---:|---:|
| **Branch** | **0.124** | **0.095** | **0.219** | **6504** |
| NetRay | 0.294 | 0.132 | 0.426 | 6504 |
| NetRay (Validate=Full) | 0.379 | 0.167 | 0.546 | 6504 |
| Blink | 0.184 | 0.171 | 0.355 | 7500 |

--- **Branch is 95% faster than NetRay, 62% faster than Blink.**

Blink's messages are 2 bytes larger each: it stores every string length in 2 bytes, while Branch and NetRay use 1 byte for short strings.

---

### Case 5: Movement, server → one player (500 per frame)

The server sends 500 movement updates per frame to one player. Each update has a position, a velocity, a direction, three flags and an animation id.

| Library | Encode | Decode | Total | Bytes / frame | Remote calls / frame |
|---|---:|---:|---:|---:|---:|
| **Branch** | **0.607** | **0.508** | **1.115** | **15004** | **1** |
| NetRay | 0.912 | 0.634 | 1.546 | 16500 | 500 |
| NetRay (Validate=Full) | 1.184 | 0.692 | 1.876 | 16500 | 500 |
| Blink | 1.019 | 1.066 | 2.085 | 16500 | 1 |

--- **Branch is 39% faster than NetRay, 87% faster than Blink.**

- **Remote calls.** NetRay makes one remote call per event: 500 calls per frame here. Branch and Blink collect a frame's events into one call.
- **Size.** Branch is also 9% smaller: when the same event repeats, Branch writes its id once for the whole run instead of once per event.

---

### Case 6: Movement, FireAll to 20 players (50 per frame)

The server broadcasts 50 movement updates per frame to 20 players.

| Library | Encode | Decode (all 20 players) | Total | Bytes / frame | Remote calls / frame |
|---|---:|---:|---:|---:|---:|
| **Branch** | **0.123** | **1.701** | **1.824** | **30060** | **1** |
| NetRay | 0.160 | 1.781 | 1.941 | 32060 | 1 |
| NetRay (Validate=Full) | 0.218 | 1.983 | 2.201 | 32060 | 1 |
| Blink | 0.608 | 1.879 | 2.487 | 33000 | 20 |

--- **Branch is 6% faster than NetRay, 36% faster than Blink.**

This is the closest case. Branch and NetRay both send a broadcast once, with a single `FireAllClients`, while Blink sends a separate copy to each player. Branch still sends 6% fewer bytes than NetRay.

---

### Case 7: Unreliable movement (200 per frame)

The server sends 200 movement updates per frame over the unreliable channel. Roblox drops unreliable packets larger than about 900 bytes, so a library has to keep every packet under that limit.

| Library | Encode | Decode | Total | Bytes / frame | Packets / frame | Largest packet |
|---|---:|---:|---:|---:|---:|---:|
| **Branch** | **0.501** | **0.344** | **0.845** | **6024** | **8** | 813 B |
| NetRay | 0.791 | 0.474 | 1.265 | 6600 | 200 | 33 B |
| NetRay (Validate=Full) | 0.979 | 0.505 | 1.484 | 6600 | 200 | 33 B |
| Blink | 0.692 | 0.737 | 1.429 | 6600 | 200 | 33 B |

--- **Branch is 50% faster than NetRay, 69% faster than Blink.**

NetRay and Blink send each unreliable event as its own packet: 200 per frame. Branch packs them into 8 packets per frame, each safely under the limit.

# Part 2: Roblox Studio (the real engine)

## How we tested

- **The place.** A benchmark place containing all three libraries side by side, with the same schema in each. It ran as a Play session in Roblox Studio: one real server and one real client.
- **Based on NetRay's method.** The harness follows the NetRay author's own benchmark place: the same car data, 50 sends per frame, CPU time per send, bandwidth and round-trip time. We added:
  - the end-of-frame flush time;
  - remote calls per frame;
  - server → client tests;
  - decode time, measured on a real captured packet.
- **Equal instrumentation.** All three libraries were measured the same way: remote calls and payload bytes counted, the flush timed, and the receive handler timed on a real packet.
- **Numbers.** Times are **nanoseconds per message (lower is better)**. Throughput tests ran 300 frames, 3 times; the median is shown. Decode tests ran 2000 iterations, 5 times; the best is shown.

---

### Case 1: Correctness first

Before any timing, 50 cars were sent through each library and compared field by field on the server.

| Library | Cars received intact |
|---|---:|
| Branch | 50 / 50 |
| NetRay | 50 / 50 |
| Blink | 50 / 50 |

After all the timing phases, each library had also delivered **60,000 of 60,000** server → client events.

---

### Case 2: Client → server, 50 cars per frame (NetRay's own test)

| Library | `Fire` call | Fire + frame flush | Bytes per car |
|---|---:|---:|---:|
| **Branch** | **310** | **684** | **125.5** |
| NetRay | 322 | 824 | 125.5 |
| Blink | 552 | 929 | 128.4 |

--- **Branch is 20% faster than NetRay, 36% faster than Blink** (counting the full cost: the `Fire` call plus the flush).

The `Fire` call on its own is close between Branch and NetRay: Branch is 4% faster. The difference is in building and sending the packet.

---

### Case 3: The server reads those 50 cars

The time the server needs to decode and **validate** one real packet of 50 cars.

| Library | Time per car |
|---|---:|
| **Branch** | **108** |
| NetRay | 131 |
| Blink | 375 |

--- **Branch is 21% faster than NetRay, 247% faster than Blink.**

This counts for security: validation is Branch's own defence against exploiters, and it is included in this time.

---

### Case 4: Server → one player, 100 events per frame

| Library | `Fire` call | Flush | Total | Bytes per event | Remote calls per frame |
|---|---:|---:|---:|---:|---:|
| **Branch** | **123** | 190 | **313** | **30** | **1** |
| NetRay | 1638 | 13 | 1651 | 33 | 100 |
| Blink | 257 | 186 | 444 | 33 | 1 |

--- **Branch is 427% faster than NetRay, 42% faster than Blink.**

NetRay makes one engine remote call per event, and in the real engine each of those calls is expensive. Branch makes one call per frame.

---

### Case 5: FireAll, 100 events per frame

| Library | `FireAll` call | Flush | Total | Bytes per event |
|---|---:|---:|---:|---:|
| **Branch** | 152 | **176** | **328** | **30** |
| NetRay | **119** | 287 | 406 | 32 |
| Blink | 561 | 176 | 737 | 33 |

--- **Branch is 24% faster than NetRay, 125% faster than Blink.**

To be fair: NetRay's `FireAll` call on its own is cheaper than Branch's (119 vs 152 ns). Branch spends a little more when you call it so that per-player order stays exact, and wins it back in the flush.

### Case 6: The client reads a FireAll frame

The time the client needs to decode one real packet of 50 movement updates.

| Library | Time per event |
|---|---:|
| **Branch** | **38** |
| NetRay | 45 |
| Blink | 295 |

--- **Branch is 18% faster than NetRay, 676% faster than Blink.**

### Case 7: Round trip of a function call

The client calls a server function 60 times and waits for each answer. Times are in milliseconds.

| Library | Average | Median | 95th percentile | Wrong answers |
|---|---:|---:|---:|---:|
| Branch | 20.60 | 20.62 | 21.80 | 0 |
| NetRay | 20.66 | 20.75 | 21.67 | 0 |
| Blink | 20.40 | 20.50 | 21.88 | 0 |

--- **A tie.** The round trip is decided by the network and the engine's tick, not by the library. All three are within 0.3 ms of each other, which is less than the run-to-run noise.

# Correctness tests

Speed is worth nothing if messages arrive wrong. Every Branch build must pass the following before it ships.

## Automated tests (Lune): 46, all passing

The network tests run the real generated code between one mocked server and several mocked clients.

**Networking (27 tests)**

1. Every supported type makes a round trip inside a struct, server → client.
2. Tuples, optional trailing arguments and events with no arguments.
3. Broadcasts reach the right players, once each, in order.
4. Frames that only use FireAll are shipped once through `FireAllClients`, and mixing FireAll with per-player sends keeps the exact order.
5. FireAll stays exact while the write cache switches between broadcast buffers.
6. Events with no arguments, sent in bulk, all arrive; forged "empty runs" cannot make the receiver loop forever.
7. An unreliable FireAll that has to ship early never overtakes earlier per-player events.
8. **Fuzz test:** 6 random seeds × 120 frames of random mixes of every send method, reliable and unreliable. Everything must arrive exactly, in order and under the size budget.
9. Runs of the same event are packed with one id and decode exactly.
10. Forged huge arrays of strings or Instances are refused before any memory is allocated.
11. Luau keywords (`end`, `local`, …) are refused as names, so the generated code always compiles.
12. Stepped numbers (`f32(0..1, 0.01)`): travel as a step index, arrive exact to the step, out-of-range values are clamped.
13. `Unpack`: struct fields travel as named positional values.
14. Functions: invoke, reply, errors in the handler, calls queued before a handler exists.
15. Events that arrive before a listener exists are queued and delivered.
16. A bad argument errors at the caller and never corrupts the rest of the frame.
17. Even with checks off, a nil Instance cannot corrupt the other events.
18. The server rejects malformed, oversized and out-of-range client data.
19. Unreliable events are batched per frame and split before the size budget.
20. More than 255 events: ids switch to 2 bytes automatically.
21. Edge values for half-precision floats and variable-length numbers.
22. `Sync` listeners run inline; one that yields does not corrupt later events.
23. A `Sync` listener that throws is reported as a script error, the player is never blamed, and the rest of the packet is still delivered.
24. Listeners that disconnect during an event never make their neighbours miss it.
25. Players who leave mid-frame never receive or leak data.
26. Schema mistakes are reported with the event name and line.
27. The declaration parser handles comments, escapes and long strings, and reports errors.

**Runtime (9 tests)**

1. Loads segments, skips helpers and duplicates, orders `Init` by `Dependencies`.
2. Duplicate segment names: the second one is skipped with an error.
3. `AwaitStart` resumes every waiting thread.
4. The default segment rule: names ending in `Service` are segments at any depth, other modules are helpers.
5. A bad argument to `Branch:Start` leaves Branch able to start.
6. Data paths are parsed, cached, read and checked against the template.
7. `Branch.Data` refuses NaN and infinity before they reach a save.
8. `Branch.Data`: nested observers, string keys that look like numbers (UserIds), deep template checks.
9. `Timer`: pause and resume, extending, stopping with waiting threads, callbacks that fail.

**Compiler (6 tests)**

1. Parses methods, properties and type annotations; hides lifecycle hooks from autocomplete.
2. Generates the types module and the Branch block.
3. Detects freshly created modules for templating.
4. No type annotation, however unusual, can break the generated types module.
5. Renames touch code, lookups and paths, never strings, comments or fields.
6. A module's root table is found from its final `return`, whatever its form.

**DataStore browser (4 tests)**

1. The tree view flattens only expanded nodes, sorted, with stable ids.
2. Write, remove and add on a working copy.
3. The editor's text is parsed per value type.
4. ProfileStore profiles and their session lock are detected.

**Syntax check.** All 114 source files of the runtime and plugin must compile.

## Mutation testing

To check that the tests really catch bugs, we deliberately broke the network code in 6 key places, one at a time. The tests caught **6 out of 6**.

## Studio Play checks: 13 / 13

A test place runs these checks in a real Play session:

1. Every type makes a round trip client → server → client.
2. Argument checks catch bad values in Studio.
3. 300 unreliable events sent in one frame all arrive (batched).
4. The total of those unreliable events is exact.
5. A FireAll broadcast arrives.
6. A function `Invoke` returns the handler's result.

9. `Branch.Data.Client` sees the server's writes.

# Notes

**Why Lune and Studio numbers differ.**
- Lune runs Luau without Roblox's engine, so its absolute times are not Studio times. Compare the libraries against each other, not the milliseconds.
- In Studio, the remote calls themselves are expensive. That is why NetRay's one-call-per-event design costs so much more there (Studio case 4) than in Lune (Lune case 5).

**Where Branch is not ahead.**
- The function round trip is a tie.
- NetRay's `FireAll` call on its own is cheaper (Studio case 5).
- Decoding NetRay's car benchmark in Lune is about even (Lune case 1).

In each of these, Branch still wins, or ties, on the total.

**Where the speed comes from:**
- **Packed booleans.** Booleans and "is this optional value present" flags are packed into shared bits.
- **Fixed positions.** Fixed-size fields are written at known positions, with one space check per event.
- **Short lengths.** Lengths use 1 byte when they are short.
- **Runs.** A repeated event is written without its id, and the id is sent once for the whole run.
- **Few remote calls.** Each player's events are batched into one remote call per frame, and a broadcast is sent once with `FireAllClients`.
- **No per-send allocation.** Sending allocates no tables.
- **Fast dispatch.** Received events are dispatched by array lookup, not by a chain of `if`s.

**Safety is included in the numbers.** Every Branch result above includes server-side validation of client data: bounds, ranges, NaN, Instance classes and array lengths. A malformed packet is dropped and reported through `Branch.Network.OnReject`. NetRay shipped with validation off in these tests; its `Validate=Full` rows show the cost of turning it on.

## About the benchmark code

The benchmark harness compiles Branch's networking with the Branch Studio compiler, which is not open source, so the harness is not in this repository. The runtime tests in this repository run with `lune run tests/runtime.test.luau`.
